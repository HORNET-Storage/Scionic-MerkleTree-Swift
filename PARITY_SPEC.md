# Scionic Merkle Tree — Cross-Language Parity Specification

This document defines the **compliance contract** for any language port of the [Scionic Merkle Tree](https://github.com/HORNET-Storage/Scionic-Merkle-Tree). If your implementation produces the exact values listed here for the same inputs, it is byte-compatible with the Go reference implementation.

All reference values were generated by the Go library (v2) and independently verified by the Swift port.

---

## How This Spec Works

Each layer builds on the previous. Start from Layer 1 and work up. A port that passes all layers is fully compatible.

- **Layer 1** — Verify your primitives (CBOR, base encodings, varint) produce correct bytes
- **Layer 2** — Verify your Classic Merkle Tree produces identical roots and proofs
- **Layer 3** — Verify your leaf hashing pipeline (CBOR → SHA-256 → CID → base32lower) produces identical CID strings
- **Layer 4** — Verify your DAG creation from a filesystem produces the identical root hash
- **Layer 5** — Verify your DAG operations (verify, serialize, transmit, diff) work correctly

## Layer 1: Primitives

### 1.1 CBOR Encoding

The library uses `fxamacker/cbor` v2 with **default encoding mode**:
- Structs → CBOR maps (major type 5) with **PascalCase field names** as string keys
- Field order follows **struct definition order** (not sorted)
- `nil` byte slices → CBOR null (`0xf6`)
- Empty byte slices `[]byte{}` → empty byte string (`0x40`)
- `nil` arrays → CBOR null (`0xf6`)
- Empty arrays `[]T{}` → empty array (`0x80`)
- Integers use **shortest encoding** (major type 0 for ≥ 0)

Verify these CBOR encodings:

| Input | Expected Hex |
|-------|-------------|
| unsigned int 0 | `00` |
| unsigned int 23 | `17` |
| unsigned int 24 | `1818` |
| unsigned int 42 | `182a` |
| unsigned int 255 | `18ff` |
| unsigned int 256 | `190100` |
| unsigned int 1000 | `1903e8` |
| unsigned int 65535 | `19ffff` |
| unsigned int 65536 | `1a00010000` |
| unsigned int 1000000 | `1a000f4240` |
| negative int -1 | `20` |
| negative int -10 | `29` |
| negative int -100 | `3863` |
| empty byte string | `40` |
| byte string [0x01, 0x02, 0x03, 0x04] | `4401020304` |
| empty text string | `60` |
| text string "hello" | `6568656c6c6f` |
| text string "file" | `6466696c65` |
| empty array | `80` |
| array [1, 2, 3] | `83010203` |
| empty map | `a0` |
| null | `f6` |
| false | `f4` |
| true | `f5` |

**Critical**: map key order must be preserved (not sorted). Encoding `{"B": 1, "A": 2}` and `{"A": 2, "B": 1}` must produce **different** bytes.

### 1.4 Varint (Unsigned LEB128)

| Value | Encoded Hex |
|-------|------------|
| 0 | `00` |
| 1 | `01` |
| 18 (0x12, SHA2-256 code) | `12` |
| 32 (0x20, digest length) | `20` |
| 81 (0x51, CBOR codec) | `51` |
| 113 (0x71, DAG-CBOR codec) | `71` |
| 127 | `7f` |
| 128 | `8001` |
| 300 | `ac02` |

### 1.5 CID Binary Format

CIDv1 with CBOR codec and SHA2-256:

```
[0x01]  = CID version 1
[0x51]  = CBOR codec (varint)
[0x12]  = SHA2-256 hash function code (varint)
[0x20]  = 32 bytes digest length (varint)
[32 bytes] = SHA-256 digest
```

Total: 36 bytes. String format: `b` + base32lower(binary)

## Layer 2: Classic Merkle Tree

The Merkle tree accepts a **map of string key → DataBlock**. Keys are sorted alphabetically. Each DataBlock serializes to bytes, which are SHA-256 hashed to form leaves. The tree uses standard binary Merkle construction with odd-length duplication.

## Layer 3: Leaf Hashing (CID Generation)

The leaf hash is generated by:
1. Constructing a CBOR map with fields in **exact order** (see below)
2. SHA-256 hashing the CBOR bytes
3. Wrapping in CIDv1 (version=1, codec=0x51, hashFunc=0x12)
4. Encoding as `b` + base32lower

### 3.1 Non-Root Leaf CBOR Field Order

```
{
    "ItemName":         string,
    "Type":             string ("file" | "chunk" | "directory"),
    "MerkleRoot":       bytes (empty=0x40 if no links, raw link bytes if 1 link, merkle root if >1),
    "CurrentLinkCount": int,
    "ContentHash":      bytes or null (SHA-256 of content, null if no content),
    "AdditionalData":   array of {"Key": string, "Value": string} sorted by key, or null
}
```

**Critical nil/empty semantics** (determines CBOR bytes):
- `nil` additionalData passed to BuildLeaf → `SortMapByKeys(nil)` returns empty map → `SortMapForVerification(emptyMap)` returns empty array → CBOR empty array `0x80` (NOT null)
- Non-nil additionalData with entries → sorted `[KeyValue]` array → CBOR array of maps

### 3.2 Root Leaf CBOR Field Order (additional fields)

```
{
    "ItemName":         string,
    "Type":             string,
    "MerkleRoot":       bytes,
    "CurrentLinkCount": int,
    "LeafCount":        int (total leaves in DAG),
    "ContentSize":      int64 (total content bytes),
    "DagSize":          int64 (total serialized size),
    "ContentHash":      bytes or null,
    "AdditionalData":   array or null
}
```

## Layer 5: DAG Operations

Once your port creates DAGs with matching root hashes, verify these operations:

### 5.1 Verification
- `dag.Verify()` passes on the DAGs from Layer 4
- Tampered leaf content causes verification to fail
- Tampered ContentSize/DagSize on root causes verification to fail

### 5.2 Directory Recreation
- `dag.CreateDirectory(outputPath)` recreates all files with exact original content
- Nested subdirectories are created correctly
- File contents match byte-for-byte

### 5.3 Serialization Round-Trip
- `dag.ToJSON()` → `Dag.FromJSON(data)` → `restored.Verify()` passes
- `dag.ToCBOR()` → `Dag.FromCBOR(data)` → `restored.Verify()` passes
- Root hash is preserved through serialization

### 5.4 Transmission
- `dag.GetLeafSequence()` produces packets in BFS order (root first)
- Applying all packets to an empty DAG reconstructs the original
- Each packet's leaf can be independently verified

### 5.5 Labels
- `dag.CalculateLabels()` assigns deterministic numeric labels
- Root is always label "0"
- Non-root leaves get "1", "2", etc. in traversal order

### 5.6 Diff
- Two DAGs with different content produce a non-empty diff
- `diff.GetAddedLeaves()` and `diff.GetRemovedLeaves()` are non-empty
- `diff.ApplyToDAG(oldDag)` produces a valid DAG

### 5.7 Partial DAG
- `dag.GetPartial(leafHashes, pruneLinks: true)` extracts a subset
- Partial DAG has fewer leaves than full DAG
- `partial.IsPartial()` returns true
- `partial.Verify()` passes using stored Merkle proofs

## Key Implementation Notes

### AdditionalData nil vs empty

This is the most common source of hash mismatches. The Go code does:

```go
additionalData = SortMapByKeys(additionalData)          // nil → empty map
SortMapForVerification(additionalData)                    // empty map → empty []KeyValue (not nil)
```

So `nil` input → CBOR empty array (`0x80`), NOT CBOR null (`0xf6`).

### Directory entry ordering

`os.ReadDir` in Go returns entries sorted by name. Your language must sort directory entries alphabetically before processing.

### Chunk naming for multi-chunk files

When a file exceeds `ChunkSize`, chunks are named by joining the relative path with the chunk index:
- `filepath.Join(relPath, "0")` for chunk 0
- `filepath.Join(relPath, "1")` for chunk 1
- etc.

Single-chunk files store data directly on the file leaf (no child chunks created).

### Link ordering

- **Directories**: links are sorted alphabetically (by CID hash string)
- **Files**: chunk links preserve insertion order (chunk 0, 1, 2...)

### Classic Merkle Tree inside parent leaves

When a leaf has >1 child link, a Classic Merkle Tree is built from the link hashes (key = hash, value = hash). The tree's root becomes `ClassicMerkleRoot`. When a leaf has exactly 1 child, `ClassicMerkleRoot` = raw UTF-8 bytes of the child's CID string.
