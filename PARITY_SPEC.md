# Scionic Merkle Tree — Cross-Language Parity Specification

This document defines the **compliance contract** for any language port of the [Scionic Merkle Tree](https://github.com/HORNET-Storage/Scionic-Merkle-Tree). If your implementation produces the exact values listed here for the same inputs, it is byte-compatible with the Go reference implementation.

All reference values were generated by the Go library and independently verified by the Swift port.

**Ports mirror the Go library's version number.** This is Swift `v2.4.0`, byte-compatible with Go `v2.4.0`, and the Rust port follows the same scheme. A port's version is a claim about *which Go release it reproduces byte for byte* rather than an independent release history: a port never bumps on its own, it bumps when it catches up to a Go release. If a port needs to ship a fix without a Go change, it appends a suffix (`v2.4.0+swift.1`) rather than moving the base version, so the parity claim stays unambiguous.

The Layer 4 fixture roots are regenerated by `tools/gofixtureroots`, which builds against a local checkout of the Go library rather than a published release, so the expectations always track the code actually under test.

---

## How This Spec Works

Each layer builds on the previous. Start from Layer 1 and work up. A port that passes all layers is fully compatible.

- **Layer 1** — Verify your primitives (CBOR, base encodings, varint) produce correct bytes
- **Layer 2** — Verify your Classic Merkle Tree produces identical roots and proofs
- **Layer 3** — Verify your leaf hashing pipeline (CBOR → SHA-256 → CID → base32lower) produces identical CID strings
- **Layer 4** — Verify your DAG creation from a filesystem produces the identical root hash
- **Layer 5** — Verify your DAG operations (verify, serialize, transmit, diff, store, partial DAGs) work correctly

The Swift port currently verifies this contract with **243 XCTest tests** (7 of which skip when the optional `spec/vectors` corpus is absent), including the 12 direct cross-compatibility vector tests plus fixture root, true file streaming, store index/cache/update APIs, store streaming, serialization, partial-DAG, batched-transmission, DAG parallel multi-chunk-file, and classic-tree parallel proof-update parity regressions.

## Layer 1: Primitives

### 1.1 CBOR Encoding

The library uses `fxamacker/cbor` v2 with **default encoding mode**:
- Structs → CBOR maps (major type 5) with **PascalCase field names** as string keys
- Field order follows **struct definition order** (not sorted)
- `nil` byte slices → CBOR null (`0xf6`)
- Empty byte slices `[]byte{}` → empty byte string (`0x40`)
- `nil` arrays → CBOR null (`0xf6`)
- Empty arrays `[]T{}` → empty array (`0x80`)
- Integers use **shortest encoding** (major type 0 for ≥ 0)

Verify these CBOR encodings:

| Input | Expected Hex |
|-------|-------------|
| unsigned int 0 | `00` |
| unsigned int 23 | `17` |
| unsigned int 24 | `1818` |
| unsigned int 42 | `182a` |
| unsigned int 255 | `18ff` |
| unsigned int 256 | `190100` |
| unsigned int 1000 | `1903e8` |
| unsigned int 65535 | `19ffff` |
| unsigned int 65536 | `1a00010000` |
| unsigned int 1000000 | `1a000f4240` |
| negative int -1 | `20` |
| negative int -10 | `29` |
| negative int -100 | `3863` |
| empty byte string | `40` |
| byte string [0x01, 0x02, 0x03, 0x04] | `4401020304` |
| empty text string | `60` |
| text string "hello" | `6568656c6c6f` |
| text string "file" | `6466696c65` |
| empty array | `80` |
| array [1, 2, 3] | `83010203` |
| empty map | `a0` |
| null | `f6` |
| false | `f4` |
| true | `f5` |

**Critical**: map key order must be preserved (not sorted). Encoding `{"B": 1, "A": 2}` and `{"A": 2, "B": 1}` must produce **different** bytes.

| Value | Encoded Hex |
|-------|------------|
| 0 | `00` |
| 1 | `01` |
| 18 (0x12, SHA2-256 code) | `12` |

| 113 (0x71, DAG-CBOR codec) | `71` |
| 127 | `7f` |
| 128 | `8001` |
| 300 | `ac02` |

### 1.5 CID Binary Format

CIDv1 with CBOR codec and SHA2-256:

```
[0x01]  = CID version 1
[0x51]  = CBOR codec (varint)
[0x12]  = SHA2-256 hash function code (varint)
[0x20]  = 32 bytes digest length (varint)
[32 bytes] = SHA-256 digest
```

Total: 36 bytes. String format: `b` + base32lower(binary)

## Layer 2: Classic Merkle Tree

The Merkle tree accepts a **map of string key → DataBlock**. Keys are sorted alphabetically. Each DataBlock serializes to bytes, which are SHA-256 hashed to form leaves. The tree uses standard binary Merkle construction with odd-length duplication.

### 2.1 Reference Root Hashes

Each test creates a tree from `map[string]DataBlock` where both key and value are the same string, and `Serialize()` returns the raw UTF-8 bytes.

## Layer 3: Leaf Hashing (CID Generation)

The leaf hash is generated by:
1. Constructing a CBOR map with fields in **exact order** (see below)
2. SHA-256 hashing the CBOR bytes
3. Wrapping in CIDv1 (version=1, codec=0x51, hashFunc=0x12)
4. Encoding as `b` + base32lower

### 3.1 Non-Root Leaf CBOR Field Order

```
{
    "ItemName":         string,
    "Type":             string ("file" | "chunk" | "directory"),
    "MerkleRoot":       bytes (empty=0x40 if no links, raw link bytes if 1 link, merkle root if >1),
    "CurrentLinkCount": int,
    "ContentHash":      bytes or null (SHA-256 of content, null if no content),
    "AdditionalData":   array of {"Key": string, "Value": string} sorted by key, or null
}
```

**Critical nil/empty semantics** (determines CBOR bytes):
- `nil` additionalData passed to BuildLeaf → `SortMapByKeys(nil)` returns empty map → `SortMapForVerification(emptyMap)` returns empty array → CBOR empty array `0x80` (NOT null)
- Non-nil additionalData with entries → sorted `[KeyValue]` array → CBOR array of maps

### 3.2 Root Leaf CBOR Field Order (additional fields)

```
{
    "ItemName":         string,
    "Type":             string,
    "MerkleRoot":       bytes,
    "CurrentLinkCount": int,
    "LeafCount":        int (total leaves in DAG),
    "ContentSize":      int64 (total content bytes),
    "DagSize":          int64 (total serialized size),
    "ContentHash":      bytes or null,
    "AdditionalData":   array or null
}
```

### 4.4 Nested Chunked File

A file larger than the chunk size, nested several directories deep, is the case that previously diverged across platforms: Go named chunk leaves with `filepath.Join(relPath, index)`, which put a backslash into every chunk `ItemName` on Windows and a forward slash elsewhere, and those bytes are hashed into the root. Both implementations now name chunk leaves with the bare index, so a chunk `ItemName` contains no separator and this root is identical on every platform.

Fixture:

```
input/
└── nested/
    └── inner/
        └── large.bin  (10,000 bytes: UInt8(index % 251))
```

| Root CID | Leaves | Chunk Leaves | Content Size | DAG Size |
|----------|--------|--------------|--------------|----------|
| `bafireicgewyfpgq5ywxpx7wddgo56ghfeq6a5sszivzwt4h32xufds4s3u` | 7 | 3 | 10,000 | 11,996 |

Chunk `ItemName` values for this fixture are exactly `"0"`, `"1"` and `"2"`.

## Layer 5: DAG Operations

Once your port creates DAGs with matching root hashes, verify these operations:

### 5.1 Verification
- `dag.Verify()` passes on the DAGs from Layer 4
- `DagStore.Verify()` and `DagStore.VerifyStreaming()` pass for full DAGs
- `DagStore.VerifyStreaming()` verifies through metadata-first store access and does not materialize the full DAG with `ToDag()`
- `DagStore.VerifyStreaming()` verifies partial DAGs using stored Merkle proofs instead of requiring all children to exist locally
- Tampered leaf content causes verification to fail
- Tampered `ContentSize` or `DagSize` on root causes verification to fail when full DAG size validation is possible

### 5.2 Directory Recreation
- `dag.CreateDirectory(outputPath)` recreates all files with exact original content
- Nested subdirectories are created correctly
- File contents match byte-for-byte

### 5.3 Serialization Round-Trip
- `dag.ToJSON()` → `Dag.FromJSON(data)` → `restored.Verify()` passes
- `dag.ToCBOR()` → `Dag.FromCBOR(data)` → `restored.Verify()` passes
- Root hash is preserved through serialization
- Partial DAG JSON round-trips preserve stored proof keys, proof leaf values, siblings, and path bits

### 5.4 Transmission
- `dag.GetLeafSequence()` produces packets in BFS order (root first)
- Applying all packets to an empty DAG reconstructs the original
- Each packet's leaf can be independently verified
- `DagStore.AddTransmissionPacket()` verifies root leaves, child leaves, parent links, and required Merkle proofs before storing
- Batched transmission packets round-trip through JSON and CBOR
- Current batched encoders include `PacketIndex` and `TotalPackets` in BFS batch order so transports can negotiate bounded sliding windows without weakening per-packet verification
- Batched decoders accept legacy packets that omit both counters and surface zero values, preserving stop-and-wait compatibility with previously stored and deployed data
- Batch-size checks use the CBOR-encoded packet size, not JSON text size
- Applying batched packets to an empty `Dag` reconstructs and verifies the original
- Applying batched packets to an empty `DagStore` reconstructs and passes `VerifyStreaming()`
- Partial DAG batched transmission preserves the original partial parent proofs when not all children are present in a batch

### 5.5 Labels
- `dag.CalculateLabels()` assigns deterministic numeric labels
- Root is always label "0"
- Non-root leaves get "1", "2", etc. in traversal order

### 5.6 Diff
- Two DAGs with different content produce a non-empty diff
- `diff.GetAddedLeaves()` and `diff.GetRemovedLeaves()` are non-empty
- `diff.ApplyToDAG(oldDag)` produces a valid DAG

### 5.7 Partial DAG
- `dag.GetPartial(leafHashes, pruneLinks: true)` extracts a subset
- Partial DAG has fewer leaves than full DAG
- `partial.IsPartial()` returns true
- `partial.Verify()` passes using stored Merkle proofs
- Partial DAGs with single retained leaves and proof-bearing retained leaves both serialize, transmit, and verify

### 5.8 Store Index and Parent Hash Updates
- `DagStore.BuildIndex()` builds parent-before-child traversal order from either cached child→parent relationships or BFS traversal
- `HasIndex`, `GetIndex`, `ClearIndex`, `AddToIndex`, and `MarkIndexBuilt` match the Go store lifecycle
- `IterateDagWithIndex()` returns leaf hashes and parent hashes without loading leaf content
- `UpdateParentHashesStreaming(batchSize)` updates stored parent hashes in bounded batches and preserves existing in-memory content

## Key Implementation Notes

### AdditionalData nil vs empty

This is the most common source of hash mismatches. The Go code does:

```go
additionalData = SortMapByKeys(additionalData)          // nil → empty map
SortMapForVerification(additionalData)                    // empty map → empty []KeyValue (not nil)
```

So `nil` input → CBOR empty array (`0x80`), NOT CBOR null (`0xf6`).

### Directory entry ordering

`os.ReadDir` in Go returns entries sorted by name. Your language must sort directory entries alphabetically before processing.

### Chunk naming for multi-chunk files

When a file exceeds `ChunkSize`, each chunk leaf is named with the **bare chunk
index** — `"0"`, `"1"`, `"2"` — and nothing else. The relative path is **not**
joined in.

This is hash-visible, because the chunk `ItemName` is part of the leaf hash.
Naming chunks with `filepath.Join(relPath, index)` was the original Go behaviour,
and it made every chunked-file root CID depend on the OS that built the DAG
(`\` on Windows, `/` elsewhere). Go fixed this in `processFile`,
`processFileParallel` and `buildGitFileLeaf`; the comment in `dag/dag.go` states
the rule directly:

> Chunk names are synthetic labels, not filesystem paths. Naming them with
> `filepath.Join` made the leaf CID depend on the OS that built the DAG
> ('\' on Windows, '/' elsewhere). A bare index matches processFileParallel
> and buildGitFileLeaf and is platform-independent.

Both the sequential and parallel Go paths build chunk 0 as
`CreateDagLeafBuilder("0")` and every later chunk as
`CreateDagLeafBuilder(strconv.Itoa(index))`.

A port that joins the path here will match no chunked-file reference value in
§4.3 or §4.4, and its roots will differ across platforms. §4.4 exists precisely
to pin this case.

Single-chunk files store data directly on the file leaf (no child chunks created).

### Link ordering

- **Directories**: links are sorted alphabetically (by CID hash string)
- **Files**: chunk links preserve insertion order (chunk 0, 1, 2...)

### Classic Merkle Tree inside parent leaves

When a leaf has >1 child link, a Classic Merkle Tree is built from the link hashes (key = hash, value = hash). The tree's root becomes `ClassicMerkleRoot`. When a leaf has exactly 1 child, `ClassicMerkleRoot` = raw UTF-8 bytes of the child's CID string.

### Streaming file creation

Ports must read chunked files incrementally. Loading the full file into memory and then slicing it can still produce correct hashes, but it is not acceptable for mobile-scale parity with the Go implementation.

### Store-backed streaming verification

`DagStore.VerifyStreaming()` must verify via store APIs. Root CID verification may run without a full DAG; ContentSize/DagSize recalculation is reserved for callers that already have a full DAG in memory.

## Generating Reference Values

```bash

go test -v -run TestCrossCompatLeafHashes ./tests/
```
